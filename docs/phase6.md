## 利用できる機能

ワークスペースのHomeとサイドバーから`/app/w/[workspaceId]/handoffs`へ移動できます。

- 一覧・キーワード検索、状態・引き継ぎ元・引き継ぎ先での検索、自分宛ての一覧、20件単位のページング。
- 新規作成、下書きの編集、送信、受領、改訂して再確認を依頼、完了。
- タイトル、引き継ぎ元/先、作業概要・経緯、現在の進捗、完了済み作業、未完了作業、注意事項、次の行動。
- 関連Issue・Project・WikiをIDで指定。検索して30件まで追加できます。
- 詳細、読み取り専用の過去版、送信・受領・完了の履歴、操作者と日時。
- Issue/Project詳細とFlow Mapの詳細パネルから「この情報から引き継ぎを作る」。Wikiにも関連Handoffを表示。
- Flow MapのHandoffノード、種類別検索、既存資料との線、Issueからの隣接取得と関連Handoff表示。
- スマートフォンでは一覧・入力欄を1列にし、既存のライト/ダークテーマと共通UIを再利用。

Issue/Projectから作成するときは、現在の本文・状態と直接関連する資料を最大30件、未保存の候補として取得します。Projectでは閲覧可能な実Issueに基づく完了件数と、候補に含まれる完了/未完了の課題を提示します。全件を無制限に読み込みません。ユーザーが内容・受取人・資料を確認して下書きを保存し、詳細画面から送信します。

## 状態と権限

| 操作 | 権限・動作 |
| --- | --- |
| 作成 | Owner/Admin/Member。引き継ぎ元はログインした本人で固定 |
| 下書き閲覧 | 作成者とOwner/Admin。受取人でも送信前は閲覧不可 |
| 下書き編集・送信 | 現在も編集可能な役割を持つ引き継ぎ元本人のみ。管理者の代理送信なし |
| 送信後の閲覧 | 同一WSの現在のメンバー。Viewerも閲覧可能 |
| 受領 | 現在の版に指名された受取人本人のみ。Viewerも受領可能 |
| 改訂 | 引き継ぎ元本人が変更理由を記入して新しい版を送信 |
| 完了 | 現在の版を受領した受取人本人のみ |

`下書き → 確認待ち → 受領済み → 完了`の順で進みます。確認待ち・受領済みで重要な変更があった場合、元の版を上書きせず、第N+1版として再送します。状態を確認待ちに戻し、以前の受領記録を残したまま新しい版の受領を求めます。完了後の改訂は行えません。
以前の提案設計では受領後に別Handoffを作る案でしたが、今回の再確認要件に合わせ、同じHandoff内で改訂版と受領記録を分けて保存しています。旧`cancelled`状態も削除せず、旧データとして閲覧可能にしています。

送信はアプリ内の状態更新と共有です。メール・外部通知は追加していません。受取人は「自分宛て」から確認します。

## 送信時の記録と最新リンク

- 下書きは関連IDを保持し、送信時にDB内で内容を取り直してスナップショットを作成します。クライアント指定のスナップショットは採用しません。
- 送信版にはタイトル、元/先のIDと当時の表示名、6つの本文、関連資料のID・種類・タイトル・版・状態・更新日・本文抜粋を保存します。Issueの番号・優先度・期限、既存の関連メモも含めます。
- 重要な本文はHandoff自身の各欄に10,000文字まで保存できます。関連資料の本文は各先頭6,000文字までの抜粋とし、省略フラグと画面の説明を付けています。Wikiの画像そのものや全履歴は複製しません。
- 「送信時点の記録」と「最新情報へのリンク」を別の欄で表示し、元資料の版が変わったら更新ありと表示します。
- 旧版と旧受領記録は改訂後も保持します。受領者・受領日時・内容の版、完了日時を記録します。
- 最近100版・100件の受領/操作履歴を画面に表示します。古い送信版は削除せず、版指定のURL/APIから確認できます。
- 履歴検索は現在の内容に加え、送信済みのタイトル・概要・当時の人名・関連資料名も対象にします。引き継ぎ先フィルターは過去の送信先も含み、「自分宛て」は現在の引き継ぎ先を判定します。

送信は資料の内容をWS内に共有する操作です。そのため、関連資料は未削除・共有中のIssue/Project/公開Wikiに限定します。元資料を後で非公開にしても、既に共有した送信記録は保持します。この点を送信確認に明記しています。最新ページを開くときは、その時点の閲覧権限を再確認します。

## セキュリティと競合

- ユーザーのSupabase AuthセッションでAPI/RPCを使用します。通常操作でService Role Keyを使用しません。
- APIの認証・Origin検証・WS所属確認と、既存テーブル/新規受領表のRLSを併用します。新しいビュー/検索関数は`security invoker`です。[SupabaseのRLS仕様](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 更新用private関数では匿名・特権JWTを拒否し、所属・役割・引き継ぎ元・受取人・両端の同一WSを再検証します。
- 所属管理・既存機能と同じWS行ロックを取り、資料の状態と受取人が途中で変わる競合を防ぎます。
- 受領・完了には、表示中のリソース更新版と送信内容版の両方を指定します。古い版による受領や二重受領は成功扱いにしません。
- 受領表・送信版・Handoff表への利用者の直接書込みを許可しません。受領表は両端が同一WSの版を参照します。
- 関連資料が後から読めなくなった場合、編集時にその参照を黙って落とさず保存を拒否します。閲覧権限を確認してから改訂してください。
- タイトル200文字、本文各10,000文字、変更理由1,000文字、関連30件、検索200文字、ページ位置10,000までを検証。HTMLは実行せず文字列表示します。
- 初回送信前の下書きや、その関連線をViewerのFlow Mapに表示しません。送信済みスナップショットの閲覧権限は親Handoffを継承します。

1. 承認された環境でPhases 2→3→4→5の適用状況とバックアップを確認します。既存Handoff/送信版の件数・状態・元/先の整合性を確認します。

4. 旧形式の送信版は削除せず表示を維持します。送信元/受取人が列に記録されていない旧版には新しい受領を付けず、元の担当者が内容を確認して改訂送信してください。不整合のある旧データは自動で所有者を割り当てません。

環境変数の追加、メール設定、AIキーの追加設定は不要です。切戻し時も送信版・受領履歴を削除せず、アプリ側のHandoff導線を止めてデータを保持します。
